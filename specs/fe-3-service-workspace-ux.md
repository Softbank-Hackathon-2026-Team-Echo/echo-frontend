## 1. 문제

화면 모양이 아니라 **일의 단위**가 어긋났다. 사용자는 서비스 하나를 올리고 고치고 옮기려 하는데, 화면은 조직 단위로 흩어져 있다.

| 사용자가 하려는 일 | 지금 겪는 일 | 출처 |
|---|---|---|
| 서비스 상태 보기 | 대시보드가 하나뿐이고 처음 찾은 서비스의 지표만 보인다 | 지민 · `DashboardPage` |
| 변수 넣기 | 첫 배포 전에는 못 넣고, 한 키씩 넣고, 환경마다 반복한다 | 도현 |
| DB 앱 첫 배포 | 실패 → 변수 → 재배포를 환경마다 해서 4단계가 된다 | 도현 |
| 실패 원인 찾기 | 컨테이너 로그와 종료 코드가 없어 클러스터에 직접 들어갔다 | 도현 · 회의록 |
| 다른 클라우드로 옮기기 | 재난 없이는 입구를 찾기 어렵고, 예비가 없으면 막힌다 | 도현 |
| 처음 쓰기 | 배포에 무엇이 필요한지 안내가 없다 | 도현 · 회의록 |

## 2. 설계 원칙

1. **서비스가 작업의 중심이다.** 서비스 하나의 상태 · 배포 · 변수 · 이전이 한 곳에 있다.
2. **조직 화면은 고르는 곳이다.** 전체 상태를 보고 서비스로 들어간다.
3. **변수는 묶음으로 다룬다.** `.env` 를 붙여 넣고 여러 환경에 한 번에 넣는다.
4. **바꾼 뒤에 할 일을 놓치지 않게 한다.** 변경을 모아 보이고 한 번에 적용한다.
5. **실패는 다음 행동까지 보여 준다.** 원인과 고칠 곳을 같은 화면에 둔다.
6. **값을 지어내지 않는다.** 변수 값은 쓰기 전용이고, 공유되는 트래픽은 공유된다고 밝힌다.

## 3. 화면 구조

```text
/o/:slug                      조직 개요: 서비스 카드 · 환경 상태 · 재난 · 비용
/o/:slug/services             서비스 목록 (행을 누르면 작업 공간)
/o/:slug/services/:id         서비스 작업 공간
    Overview                  지금 대시보드의 서비스 부분: KPI · 트래픽 · 그래프 · 토폴로지
    Deployments               이력 · 진행 · 로그 · 실패 원인 · 되돌리기
    Variables                 키 × 환경 표 · 붙여넣기 편집 · 변경 적용
    Migration                 이 서비스의 준비 상태 · 이전 시작 · 기록
    Settings                  저장소 · 헬스 경로 · 포트 · 삭제
/o/:slug/evacuation           재난 대응 (조직 단위, 그대로)
/o/:slug/migrations           전체 이전 기록 (조직 단위, 그대로)
/o/:slug/security · audit     그대로
```

탭은 주소로 남긴다(`?tab=variables`). 서비스 공통 머리에는 이름 · 공개 주소 · 서비스 중 환경 · Deploy 를 둔다.

서비스 카드는 Railway 프로젝트 화면처럼 상태를 한눈에 보인다: 이름 · 서비스 중 환경 · 트래픽 비율 · 최근 배포 결과 · 적용 대기 변수 수.

트래픽 비율과 DB 쓰기 담당은 조직 전체 공유다. Overview 와 Migration 에 공유 안내를 그대로 둔다. 지표는 서비스별로 나뉜다(서버가 앱 네임스페이스로 거른다).

## 4. 환경 변수 화면

### 4-1. Railway 에서 가져오는 것

| Railway | EchoPort | 서버 변경 |
|---|---|---|
| RAW Editor: `.env` 붙여넣기 | 붙여넣기 편집기. 파싱 결과를 표로 미리 보고 저장 | 없음 |
| New Variable 폼 | 한 줄 추가 유지 | 없음 |
| Suggested variables: 저장소 `.env.example` 스캔 | 저장소 예시의 빠진 키 표시 | 필요 (W2) |
| Staged changes: 변경 수 배너 · 항목 취소 · Deploy | 적용 대기 막대 · 한 번에 재배포 | 없음 |
| Sealed: 값을 다시 볼 수 없음 | 이미 모든 값이 쓰기 전용이다 | 없음 |
| Reference · Shared variables | 이번에는 하지 않는다 | 큼 |

### 4-2. 가져오지 않는 것과 이유

- **값 비교 diff**: 우리 값은 다시 읽을 수 없다. 키 · 버전 · 적용 상태만 보인다.
- **저장 전 스테이징**: 서버가 저장 즉시 새 버전을 만든다. 이미 있는 `pendingRedeploy` 로 "저장됨, 적용 전" 을 보인다.
- **항목별 변경 취소**: 위와 같은 이유로 되돌릴 이전 값을 화면이 모른다.

### 4-3. Railway 에 없는 우리 화면: 키 × 환경 표

| Key | aws-tokyo | gcp-seoul | onprem-k3s |
|---|---|---|---|
| DATABASE_URL | v3 적용됨 | v2 재배포 필요 | 없음 |
| API_KEY | v1 적용됨 | 없음 | 없음 |

서비스 중 환경에 있는 키가 도착 환경에 없으면 이전이 막힌다(C-SEC-1). 이 표가 그 원인을 이전 전에 보여 준다. "없음" 칸에서 바로 값을 넣는다. 멀티 클라우드 플랫폼이라서 필요한 화면이고 시연에서 차별점이 된다.

### 4-4. 붙여넣기 흐름

```text
Paste .env → 키·값 파싱 → 미리 보기(새 키 · 값 교체 · 오류 · 예약 이름)
          → 적용 환경 체크(aws-tokyo, gcp-seoul) → Save
          → 키마다 결과 표시 → 적용 대기 막대
```

- 지금 API 는 키 하나씩 `PUT` 이다. 화면이 키 × 환경 수만큼 부른다. 실패한 키만 남겨 다시 시도할 수 있게 한다
- 환경마다 값이 달라야 하는 키는 환경을 하나만 체크해서 따로 넣는다
- 값은 다이얼로그 state 에만 두고 닫으면 지운다. 미리 보기에서 값을 가린다
- 40개 한도와 예약 이름은 저장 전에 막는다

### 4-5. 적용 대기 막대

서비스 작업 공간 어느 탭에서나 보인다: `gcp-seoul 2개, aws-tokyo 1개 변수가 적용 전입니다 [변경 적용]`.

`변경 적용` 은 브랜치를 다시 묻지 않고 그 환경의 현재 커밋(`commitSha`)으로 배포한다. 서비스 중 환경을 바꾸면 예비 따라가기가 자기 값으로 따라온다. 예비만 대기 중이면 그 환경에 배포한다.

## 5. 배포 화면

- **요구 사항 안내**: 서비스 등록 때 Dockerfile · 헬스 경로 · 포트 · 필수 변수를 체크리스트로 보인다
- **실패 화면**: 원인 → 로그 → 다음 행동 순서. 행동은 환경 변수 확인 · 같은 커밋으로 재배포 · AI 진단(생기면)
- **로그**: Build · Deploy 탭 유지. 컨테이너 로그는 W3 뒤에 Deploy 탭에 붙인다
- **예비 환경**: 첫 배포 때 "예비도 함께 띄우기" 선택. 시연 시나리오가 정해진 뒤 넣는다(W4)

## 9. 완료 기준

1. 서비스 목록에서 행 하나를 누르면 그 서비스의 상태 · 배포 · 변수 · 이전에 갈 수 있다
2. 서비스가 둘 이상일 때 서비스마다 자기 지표가 보인다
3. `.env` 를 한 번 붙여 넣어 두 환경에 저장하고, 재배포까지 버튼 두 번으로 끝난다
4. 이전 도착 환경에 없는 키가 이전 전에 보인다
5. 값이 화면 · 주소 · 저장소 · 로그에 남지 않는다
6. 라이트 · 다크 · projector, 한국어 · 일본어에서 확인한다
